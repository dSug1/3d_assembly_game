# `IN11` — is rule 2bis's free rotation PATH-DEPENDENT?

**Status: queued, and ⭐ UNBLOCKED — it needs no object model.** This is a debugging row,
not a feature row: it asks a question about code that already ships, and the answer is
reachable headlessly today.

⭐ Raised 2026-09-15 from the owner's `TECHNIQUE_CATALOG.md` §2.1, whose warning is about
trackballs but lands on our own rotation.

## The question

⛔ **Does dragging out and back by a DIFFERENT route return the object to the orientation
it started in?**

## Why there is reason to think it does not

[`src/render/scene.ts`](../../../src/render/scene.ts) applies 2bis as a **per-frame
increment** onto the pose the object already has:

```ts
screenPlaneRotation(cur, grip.frame, s.x - grip.prev.x, s.y - grip.prev.y, radPerMm)
```

⭐ The axes are latched at press and both terms are world-frame, which is the fix for a
REAL defect found by finger on 2026-09-13 (*"the yaw is in world coordinates while the
pitch is in object coordinates"*) — that part is right and must not be undone.

⛔ But **rotations about two fixed axes do not commute.** Right-then-up and up-then-right
are different orientations, so the result is a function of the PATH the finger took, not
only of where it ended up:

```
R_yaw(a)·R_pitch(b)  ≠  R_pitch(b)·R_yaw(a)
```

⚠ **Retracing the SAME path backwards does telescope to identity** — every increment is
reversed in reverse order. That is why this will feel correct in a tuning session and only
betray a user mid-assembly, who lets go, reconsiders, and drags back a different way.

## Why it matters HERE and not in an inspection tool

For free inspection, path dependence is harmless and arguably desirable. ⛔ For assembly it
erodes the thing the whole design rests on: the user is aligning a part with a mating
feature, and *"put it back the way it was"* has to work. The catalog's phrasing is that it
**erodes trust**, and `IN6` (undo) does not cover it — undo is a discrete snapshot stack,
while this is a continuous gesture that silently fails to return.

## ⭐⭐ Write the vector FIRST, and make it able to fail

This is the rare defect on this project that a green suite CAN see, so it must be written
as a vector before anything is changed:

1. **The square path.** From identity, drive `+x`, `+y`, `−x`, `−y` in equal steps back to
   the starting point. Assert the final quaternion is identity to a stated tolerance.
   ⚠ It should FAIL against today's code — per `CONSTRAINTS` §3, a vector that passes both
   ways tests nothing. **Confirm it fails before trusting it.**
2. **The order pair.** Right-then-up against up-then-right, same totals. Assert whether
   they agree, and record the angular separation as a NUMBER — that is the size of the
   effect, and it decides whether this is worth changing at all.
3. ⛔ **Step the fixture with integers**, not a float loop. Mistake shape 5 (my own
   fixtures) cost four false alarms in one session, one of them a float loop taking an
   extra step.

⚠ **Sweep the drag magnitude.** The separation grows with total angle: at 5° of travel it
may be under the pointer noise and irrelevant; at 90° it will not be. **The answer is a
curve, not a yes/no**, and the decision below depends on where it crosses perceptibility.

## The two candidate fixes, if the number turns out to matter

| | what it does | cost |
|---|---|---|
| **A — keep incremental** | do nothing; record the measured separation and the drag angle at which it exceeds the pointer noise | free, if the number is small |
| **B — make the pose a pure function of the TOTAL displacement from the press anchor** | `pose = R_yaw(Σdx)·R_pitch(Σdy)·poseAtPress` — path-independent by construction, and the round trip closes exactly | ⚠ changes the feel of every long drag, and interacts with the roll hand-off (2quinte replaces yaw/pitch mid-gesture, so "total since press" needs a defined origin after the switch) |

⛔ **Do not assume B is better.** B is what an arcball does, and it has its own property: the
object's orientation depends only on where the finger IS, so a finger that wanders and
returns undoes everything it did — which some hands read as the control slipping. ⭐ This
is an `IN5`-shaped question in the end: **ship both behind a config flag and A/B it by
finger**, because a guessed answer has been wrong every time on this project.

## ⚠ What this row must NOT break

* the world-frame axis composition (the 2026-09-13 defect);
* the axes latched at press (the same lesson as §1.4's `WORLD_AXIS_ALIGN`);
* the roll hand-off — once `rollCommitted` is true, 2quinte replaces yaw/pitch for the rest
  of the gesture;
* the provisional-motion rollback, which restores the pose snapshot if the release turns
  out to be a flick.

## Dependencies

`IN1` only. ⭐ **Not `3D1`** — the rotation maths is engine-free and already vectored, so
this can run at any time, including before the object model exists. ⚠ `IN3` will rewire
2bis onto the modelled placement and give it its missing precondition; doing `IN11` FIRST
means `IN3` inherits a settled answer instead of carrying the question forward.
