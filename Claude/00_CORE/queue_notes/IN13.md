# `IN13` — which touchpoint assignment ships

⚠ **THREE forks since 2026-09-16** — fork C was added the same day (`D27`, `A16`). The
sections below were written for two and are still accurate for A and B; C is at the bottom.

**Status: 🔧 OPEN BY DESIGN, and the mechanism to decide it is BUILT (2026-09-16).**
The two readings run from **one build**; the verdict is the owner's, and it is deliberately
**not due until the input system can be judged as a whole**.
`src/input/assignment.ts` · `holderDrive` in `src/input/depth_translate.ts` ·
`tests/assignment.test.ts` · fork B's vectors in `tests/depth_translate.test.ts`.
Decision: `D26`. The assignment itself: `D23` / amendment `A13`.

## The two forks

| | fork A — `ONE_FINGER_TRANSLATE` | fork B — `TWO_FINGER_TRANSLATE` |
|---|---|---|
| one touchpoint | **translates** | rotates (§2 rule 2bis) |
| second held still | rotates | **translates** (§4 rule 6) |
| standing | `A13`/`D23`, **approved by a hand** 2026-09-16 | ⭐ **the spec as written**, which `A13` amended |
| reached by | the default | `?touchpointAssignment=1`, or the menu toggle |

⭐ **Fork B is not a revert to an old commit.** Everything built after `A13` — `A14`'s
grace, `A15`'s orphan check, the gravity frame, `A11`'s deadband, `3D1`'s model — applies to
both readings unchanged. That is the finding that shaped `D26`.

## ⭐⭐ Why a flag and not two branches

**The entire behavioural difference is one inversion, in one function, at one call site**
(`scene.ts`, the `grip.mode` line). Depth and roll key on *the holder is still*; `A14`'s
grace answers *is a second touchpoint held*; `A15` asks *is the object under the finger*.
⛔ None of them care which finger translates.

| branches would have cost | the flag costs |
|---|---|
| every device pass doubled — and device passes are this project's bottleneck, with 35 of 35 defects found there | one pass covers both, except the assignment itself |
| every later row (`IN3`, `3D2`, snapping) cherry-picked twice, with silent drift the known failure | both forks get every later row for free |
| two queues, or one queue whose rows are ambiguous — and `CLAUDE.md` forbids the second | one queue, one row: this one |
| comparing across two pages loses the camera, the poses and the warm-up | ⭐ **the same hand, the same minute, the same scene** |

⚠ **And the flag has a stated expiry.** The day a fork needs something that is *not*
expressible as one inversion — a different depth trigger, a different eviction gesture, a
different rule 6bis — the flag is the wrong shape and a branch is the honest answer.
⭐ `tests/depth_translate.test.ts`'s *"the two forks are exact opposites"* vector is where
that will show up first, which is why it exists.

## ⛔⛔ The latch — the owner's rule, stricter than mine

> *"Flag allowed to latch only if no touchpoint is pressed (nothing touches the screen
> except the flag obviously)."*

⚠ I proposed latching **at press**, like `A7`'s frame. That is not enough: at press, a flip
between two fingers landing would still swap the meaning of a gesture that had already
begun. ⭐⭐ **Nothing down is the only state in which no gesture can be in flight**, so it is
the only safe moment to change what a gesture MEANS.

* A flip mid-gesture is **deferred, not dropped** — it lands the moment the last finger
  lifts, so the toggle never needs pressing twice.
* The latch is re-checked on every pointer event **and every frame**: a flip made while the
  glass is empty produces no pointer event, and the readout must not keep showing the old
  fork until the next touch.
* ⛔ It reads `router.size`, not `activeCount`: an `IGNORED` third finger is still a finger
  on the glass, and the question is *"can a gesture be in flight?"*.
* ⭐ The toggle's own touch cannot block it — the menu is a DOM panel over the canvas, so
  its events never reach the pointer router at all. The owner's *"except the flag
  obviously"* is satisfied structurally rather than by a special case.

⭐ It is the same family as §4's role latch and `A7`'s frame — decide on a discrete, visible
boundary, never mid-gesture — one level up: this latches the **rule table**, not a role
within it.

## What is on the glass

⭐ The HUD's roles line carries the live fork by name (`one-finger-translate`) and, while a
change waits, `→two-finger-translate ⛔PENDING(lift all fingers)`.
⛔⛔ **Both halves are load-bearing and neither is decoration.** `1.0.5` runs two rule
tables from one build, so **a device report that does not name the fork is
unattributable** — which is this morning's lesson (*a device report is evidence about the
code the device was running*) aimed one layer up, at the rule table rather than the build.
And a pending flip is exactly the state where the menu shows one value while the product
obeys another; unprinted, that reads as *"the toggle is broken"*.
⚠ It is deliberately **not** on the `build` line: that identifies an immutable artefact,
this changes at runtime, and merging the two would make a stable identity look mutable.

## Vectors

**12 for the assignment and its latch** (`tests/assignment.test.ts`), **5 for fork B**
(`tests/depth_translate.test.ts`), and every pre-existing `holderDrive` vector now names
fork A explicitly — a default parameter would have let them assert fork A while reading as
universal.

⭐ **Falsified on purpose, both claims that carry the design:**

| mutant | what reddened |
|---|---|
| the latch ignores what is on the glass (my *latch at press* laxity) | exactly the three latch vectors |
| fork B forgets to invert | all five fork-B vectors, including *exact opposites* — ⭐ and **no fork-A vector**, which is the containment the flag depends on |

⛔ `validateGestureConfig` refuses anything but `0` or `1`: `assignmentOf` reads everything
except `1` as fork A, so `0.5` or `2` would **look like the default** while the person who
set it believed the rule table had changed. Reachable for real from a URL.

## ⛔ What closes this row

**A holistic device comparison, and nothing else** — the owner's own condition. ⚠ Not a
tuning session: `D23`'s claim is that fork A *"puts the commonest gesture (translate) on the
EASIEST hand shape"*, and that is a claim about a whole session of assembly work, not about
one drag. ⭐ The comparison should try to confirm or refute **that sentence**.

⚠ Until then the default ships as fork A, because it is the reading a hand has approved and
a device-approved behaviour must not become reachable-only-by-flag because an option
arrived.

## ⭐⭐⭐ FORK C, added 2026-09-16 (`D27` / `A16`)

**A second touchpoint TAPPED anywhere toggles what the ongoing drag does; PRESSED, it keeps
every meaning it has now** — depth while the holder is still, roll on its x, two objects
translating their own.

| | fork C |
|---|---|
| one touchpoint | `TRANSLATE` at the start of every gesture, flipped by each tap |
| second touchpoint **tapped** | ⭐ toggles the holder between A's behaviour and B's |
| second touchpoint **pressed** | unchanged from today |
| reached by | `?touchpointAssignment=2`, or the menu |

⛔⛔ **IT IS NOT AN INVERSION, AND THAT IS WHY IT IS A FORK RATHER THAN A SETTING.** A and B
both compute the mode from **presence**; C does not use presence at all. ⭐⭐ The consequence
worth carrying into the comparison: **C structurally cannot have the defect `A14` fixed**,
because the mode no longer depends on whether a second touchpoint is down — there is no
lift-and-replace gap to translate through. ⚠ So if a hand prefers C, `A14`'s grace becomes
dead weight in that fork and `secondTouchGraceMs` stops mattering.

### ⚠ The two readings I had to choose between, and why

*"For one single ongoing touchpoint"* can mean the toggle **dies with the gesture**
(per-gesture) or **persists until tapped again** (a mode). ⭐ Per-gesture, because a *second*
touchpoint presupposes a first: with nothing held there is no gesture to toggle, and a tap
then has to keep its existing meaning. So the state has nowhere to live except the grip.
⚠ **The cost is real and is the thing to judge**: rotation costs a tap **every time**. If a
hand wants the sticky reading instead, it is a one-line move of the state out of `Held` —
and that is a device question, not a code question.

### ⛔⛔ The collision, and the rule that resolves it

A tap outside any object **already means something**: two of them fly the camera home. So a
toggling tap is **consumed** — no tap history, no verdict, no flick test — or *toggling
twice would reset the camera*, unasked, precisely while the user was switching modes.
⭐ With nothing held it toggles nothing and falls through, so the reset stays reachable on
an empty scene. ⚠ It is the rule `D10` states for an `IGNORED` touchpoint and `A15` for an
orphaned holder: **a touch that did one job does not also get to do another.**

### ⚠ Deliberately left open

A tap on a **different object**. The owner said *"anywhere"*, but a press there is already
rule 5 / 6bis's configuration and a *tap* there is a SELECTION, which `IN3` owns. ⛔ So C
toggles on a second touchpoint that is `SECOND` or `OUTSIDE`. **A question for the device
pass**, recorded rather than silently decided.

### Built

`Behaviour`, `initialBehaviour`, `toggleBehaviour`, `tapTogglesBehaviour` and `isTapRelease`
in `src/input/assignment.ts`; **`modeFor`** in `depth_translate.ts` — now the ONE place a
held object's mode is decided, for all three forks, so the branch is not in the wiring.
⭐ `isTapRelease` also **removed a duplicated tap test**: the camera-reset branch had it
inlined, and two copies of that arithmetic would have been two definitions free to disagree.

**27 vectors** on the assignment and its forks. ⭐ **Three mutants, each caught by its own
vector and nothing else:** the toggle firing with nothing held (the camera reset becomes
unreachable), a PRESS toggling (the owner's split gone), and the toggle leaking into forks A
and B (which would change two approved forks, and only after a tap — the hardest kind of
interference to reproduce).

### ⛔ Owed

**A DEVICE LOOK**, and fork C needs it more than A or B did: **nothing visible says whether
the next drag will translate or rotate.** In A and B a user can read the mode off their own
hand; in C they cannot, so the HUD prints `[TRANSLATE]` / `[ROTATE]` beside the fork name and
that readout is the only way to tell *"the toggle did not fire"* from *"I toggled twice"*.

## ⛔⛔ FORK C, DEFECT 1 — a double tap toggled TWICE *(owner, 2026-09-16, same day)*

> *"Double tap vs two single taps: it shall be discriminated by time between two taps. Check
> how Unity does that and reapply."*

**What shipped first**: every tap toggled the instant it landed. ⛔ So a **double** tap
toggled **twice** — a visible net-nothing — and the double-tap gesture could not form at all,
because the first build also *consumed* the tap to stop two toggles resetting the camera.

### ⭐⭐ Unity, as checked (Input System 1.12 docs)

| Unity | default | ours |
|---|---|---|
| `InputSettings.defaultTapTime` — max press-to-release | **0.2 s** | `tapMaxDuration` 250 ms |
| `MultiTapInteraction.tapDelay` — max gap BETWEEN taps | **2 × tapTime**; `multiTapDelayTime` **0.75 s** | `doubleTapWindow` 300 ms |
| `InputSettings.tapRadius` — movement bound | **5 px** | `doubleTapSlop` 8 mm — ⭐ mm, per `D7` |

⭐ **The owner's instinct was right and the parameter already existed**: the discriminator is
the **inter-tap delay**, and `TapHistory` has compared `gap <= doubleTapWindow` since `IN1`.
⛔⛔ **What Unity does NOT give is the other half.** Its `Tap` interaction *"triggers
immediately upon release … It does not wait to detect a second tap"* — so binding `Tap` and
`MultiTap` to one control fires the single action **twice** on a double tap. That is
precisely the defect reported here, present in Unity itself and left to the application.

### ✅ The fix

A single tap is **held for `doubleTapWindow`** and **cancelled if a second arrives** — the
classic single-vs-double-click answer. `pendingAfterTap` folds `TapHistory`'s verdict into a
pending state; `toggleDue` fires it from the **render loop**, because what is being waited
for is the *absence* of a second tap and an absence produces no event.
⚠ `METHOD`: *a threshold is only half a rule — the other half is what advances the clock.*
§1.1 cost three device reports by being driven by the very signal whose absence it was
detecting; this one was driven by the frame clock from the start.

⭐⭐ **AND IT REMOVED A RULE RATHER THAN ADDING ONE.** The *"a toggling tap is consumed"*
clause is **retired**: once a double tap is not a toggle at all, the two gestures no longer
overlap, and a double tap keeps exactly the meaning it has in forks A and B. ⚠ A special
case that disappears under a better question is the shape `METHOD` calls *when a rule needs a
window to decide, suspect the question* — arriving here from the opposite direction.

⛔ **ONE CONSTANT, not a new tunable.** The settle delay and the double-tap window are the
same quantity; two numbers would leave a tap that is neither single nor double. ⭐ The
boundary is strictly greater (`TapHistory` pairs on `<=`), so no instant can be both.

⚠ **THE COST, and it needs a hand**: the toggle now lands **300 ms** after the tap — real,
and the price of the two gestures being distinguishable at all. ⭐ Unity's own default would
make it 500-750 ms. The window now has a slider in the `⭐ FORK` menu section, and the HUD
shows `→PENDING` while a tap is waiting to be judged.

**7 more vectors**, and two mutants caught: a double tap that fails to cancel the armed
single (the reported defect, restored on purpose), and firing AT the boundary instead of
strictly after it.

## ⭐⭐⭐ FORK C, EXTENSION — the toggle picks the second finger's AXIS too *(owner, 2026-09-16)*

> *"Apply the tap toggle to the depth translation vs. roll: depending on which is toggled,
> the second touchpoint shall only control depth translation by delta position y or roll by
> delta position x (not both). Switching between the two shall indeed require the tap."*

| fork C, toggle = | holder's own drag | second finger (holder still) |
|---|---|---|
| `TRANSLATE` | screen-plane translate | **depth**, by its `dy` — roll suppressed |
| `ROTATE` | yaw / pitch | **roll**, by its `dx` — depth suppressed |

⭐⭐ **THE PAIRING IS BY KIND, AND THAT IS WHAT MAKES ONE TOGGLE ENOUGH FOR TWO FINGERS.**
`TRANSLATE` pairs the holder's screen-plane drag with the second finger's depth — both are
translations — and `ROTATE` pairs yaw/pitch with roll. So the tap answers one question, *am
I translating or rotating?*, and everything follows from it. ⚠ The alternative reading (a
second, independent toggle for depth-vs-roll) was not taken: the owner wrote *"depending on
which is toggled"*, singular, and a second toggle would need a second tap gesture to drive
it.

⛔ **The narrowing is a MASK ON TOP OF A10's GATE, not a replacement.** With the holder
moving, this is rule 6 and the second finger contributes nothing at all, in every fork —
asserted directly, because a mask that quietly replaced the gate would let a second finger
move the object during an ordinary drag.

⛔⛔ **FORKS A AND B KEEP `A12` EXACTLY**: x and y live at once, kept independent by `A11`'s
per-axis bands. ⭐ A vector varies the toggle value against forks A and B to prove the
narrowing cannot reach them — and the mutant that removes the fork check reddens **A12's own
vectors**, which is the containment stated as a failure rather than a hope.

⚠ **WHAT IT COSTS, and it is the thing to judge**: in fork C a roll and a depth push cannot
be interleaved without a tap between them. ⭐ That is the intent — no diagonal can do half
of each by accident, which is exactly what `A12` allows by design — so the comparison is
*"purity at the price of a tap"* against *"both axes always live"*.

**5 more vectors**, including *never both* asserted over every axis combination and both
toggle states. ⭐ Two mutants caught: the narrowing leaking into forks A and B, and the
pairing inverted (`TRANSLATE` keeping roll).

## ⛔⛔ FORK C, DEFECTS 2 AND 3 — the lag, and the mode that forgot itself *(owner, 2026-09-16)*

> *"There is a lag when the second touchpoint is tapped and the behavior change. It shall be
> immediate. Worst case, a double tap occurs and the behavior and movement can be reverted
> back while the camera orbit resets."*
>
> *"When the first touchpoint is released and pressed again, the movement automatically
> resets to translation. I would expect the movement resumes the behavior as it was prior to
> release."*

### ⭐⭐⭐ THE TOGGLE'S THIRD FORMULATION, AND THE SEQUENCE IS THE LESSON

| # | what it did | why it went |
|---|---|---|
| 1 | toggled on every tap at once, and **consumed** the tap so two toggles could not reset the camera | owner: a double tap toggled **twice** and the double-tap gesture could never form |
| 2 | a single tap **held for `doubleTapWindow`**, cancelled by a second — which made the gestures separable and **retired** the consume rule | ⛔ **a hand felt the 300 ms**: *"it shall be immediate"* |
| 3 | ✅ **immediate again**, and the double tap's consequences accepted explicitly | current |

⛔⛔ **So formulation 3 is formulation 1 WITHOUT the consume rule** — and that is not a
circle. ⭐ What the round trip bought is the **reason**: a double tap now toggles twice and
also resets the camera, and the owner has said in their own words that this is the right
trade. ⚠ Version 1 hid that consequence behind a special case nobody had chosen; version 3
exposes it deliberately.
⭐⭐⭐ **AND IT IS EXACTLY UNITY'S BEHAVIOUR**, which I had described as a wart: its `Tap`
*"triggers immediately upon release … does not wait to detect a second tap"*. ⚠ A hand chose
it for a reason no documentation states — **immediacy on a mode switch is worth more than the
discrimination** — and that is the transferable part.
⭐ `METHOD`: *a device judgement overturns a confident synthetic argument.* The deferral was
reasoned from first principles **and** from Unity's own parameters, and the only thing wrong
with it was a cost neither could see.

### ⛔⛔ And the mode is STICKY, which retires the cost I had argued against the fork

⚠ I read *"for one single ongoing touchpoint"* as *the toggle dies with the gesture*, put the
state on the grip, and **wrote down the consequence as a trade to be judged**: *rotation
costs a tap every time*. ⭐⭐ A hand rejected the premise, not the trade — the toggle is a
**MODE**, one latch for the session, and every new grip adopts it. So rotation costs a tap
only when **switching**, and the strongest argument against fork C turns out to have been an
artefact of my reading.
⚠ **What a vector cannot reach**: the latch lives in `scene.ts`, so *"it survives a
release"* is wiring. ⭐ What is vectored is the surface — the deferral's two functions are
**deleted, not disabled**, so a later session cannot wire them back believing they were
dormant, and a mutant that re-adds one reddens that guard.
⚠ **And one vector was deleted for asserting a false premise**: it claimed nothing in the
module "knows about a gesture", which is untrue — `isTapRelease` takes a release by design.
⛔ A vector built on a false premise is worse than none.

### ✅ What is on the glass

The HUD prints fork C's mode **even with nothing held**, since it is now the state the next
press will inherit — and in fork C no finger position reveals it. ⛔ `→PENDING` is gone with
the deferral. ⚠ `doubleTapWindow` keeps its slider: it no longer delays the toggle, but it
still decides whether two taps are one switch or a switch-back plus a camera reset.

## ⛔⛔ THE DEFAULT IS FORK C, 2026-09-16 — the owner's call after driving all three

`DEFAULT_CONFIG.touchpointAssignment` is **`2`**. Forks A and B stay one URL parameter or one
slider step away, which is what `D26`'s flag exists for.

⭐⭐ **It settles what `D26` was deferring.** That row shipped fork A as the default on the
grounds that it was the only reading a hand had approved — a default rule that was always
waiting on exactly one thing: a hand driving the alternatives. The hand has now done that.

⚠ **AND ONE THING IS WORTH STATING RATHER THAN LETTING IT PASS**: fork C is the default while
its **current build is unjudged**. Its two device reports — the toggle lag and the mode that
forgot itself — were fixed after the session that found them, so the fixes ship *with* the
default change. ⭐ The next device look therefore judges three things at once: the fixes, the
fork as a default, and whatever `1.0.6` adds. ⛔ If anything feels wrong the first move is
`?touchpointAssignment=0`: fork A is still the only fork closed by a device look of its own,
and it is one parameter away.

⭐ The vector that guards the default (`tests/assignment.test.ts`) now asserts **C**, and it
has changed exactly once. ⛔ That is deliberate — a default must not be able to move without
somebody editing a test that states what it is.
