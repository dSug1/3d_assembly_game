# `IN10` — orbit about the point under the finger, not the barycentre

**Status: queued, deliberately behind `3D1`/`3D5`.** ⭐ Raised 2026-09-15 from the owner's
`TECHNIQUE_CATALOG.md` §2.4 (raycast orbit pivot), and **queued rather than built** because
the problem it solves cannot yet be produced in this scene.

## The candidate

On gesture start, raycast under the finger; if it hits geometry, that point becomes the
orbit pivot for the gesture. On a miss, fall back to what we already do.
**Prior art**: conventional DCC/CAD practice (Maya tumble pivot, SolidWorks
rotate-about-selection), pre-1995 — see [`../../10_INPUT_TOUCH/PROVENANCE.md`](../../10_INPUT_TOUCH/PROVENANCE.md).

## Why it is not now

⛔ **`IN9` is CLOSED and was confirmed by finger.** Reopening a closed row needs a reason
the device can show, and today it cannot. ⚠ The scene holds **three** objects, not two —
spec §0's "two" is out of date (amendment A2) — but three *small* objects is still the case
where the barycentre **is** the thing being worked on, and `IN9` was confirmed by finger
against all four barycentre candidates they produce. The catalog's argument is explicitly
about scale — *"orbiting the bounding-box centre of the whole model is nearly useless once
the model is large"* — and that condition is `3D5`, the carried-unclosed risk that **the
assembly TREE has never held more than two objects**, which is a different thing from how
many objects sit loose in a scene.

⭐ So the trigger for this row is not a date, it is a scene: **the first time an assembly is
large enough that the barycentre is not the thing being worked on.**

## What would have to be decided, not discovered

⚠ Our rule 1 pivot is not a plain bounding-box centre — it is *the barycentre of an object
subset with the smallest perpendicular distance to the finger's ray*, chosen among
`2^N − N − 1` candidates and shown as the yellow marker. A raycast pivot is a **different
rule**, not a tuning of this one, and three things collide:

1. **The marker means something.** Double-tap flies the camera home to *the last yellow
   target*. If the pivot becomes a raycast hit, "home" has to be redefined or the reset
   goes somewhere the user never orbited.
2. **Pivot popping.** The catalog's own risk: either persist the pivot until the selection
   changes, or animate the transition over ~120 ms. ⭐ We already have the easing machinery
   for that in `camera_reset.ts`, and the same rule applies — ease the ORBIT PARAMETERS,
   never the transform.
3. ⛔ **A raycast pivot on a HELD object would fight rule 6.** The orbit centre is already
   suppressed while an object is held, for a reason (`orbitCentreGraceMs` and the
   anchor-is-not-an-orbit rule). Any raycast pivot has to respect that suppression.

## Dependencies

`IN9` (built), `3D1` (a real object model to raycast against), and in practice `3D5` —
which is the row that makes the case.
